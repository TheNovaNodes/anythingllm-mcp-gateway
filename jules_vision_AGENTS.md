# Инструкции для ИИ-агентов (Jules Vision)

Добро пожаловать в репозиторий `anythingllm-mcp-gateway`! Этот документ (`jules_vision_AGENTS.md`) создан для того, чтобы помочь ИИ-агентам (таким как я) эффективно и безопасно работать с кодовой базой.

Здесь собраны ключевые особенности архитектуры, инструменты для проверки качества кода и советы, основанные на анализе репозитория.

---

## 1. Стек и зависимости

Проект представляет собой шлюз протокола Model Context Protocol (MCP) для интеграции с семантической памятью AnythingLLM.

*   **Язык:** Python 3.10+ (поддерживаются 3.10, 3.11, 3.12).
*   **Основной фреймворк MCP:** `mcp>=1.0.0` (FastMCP).
*   **Сетевые запросы:** `requests>=2.28.0` (взаимодействие с REST API AnythingLLM).
*   **База данных:** SQLite с поддержкой полнотекстового поиска FTS5 (используется встроенный модуль `sqlite3`).
*   **Тестирование:** `pytest>=7.0.0`, `pytest-cov>=4.0.0` (определены в `dev` зависимостях `pyproject.toml`).
*   **Менеджер пакетов и сборка:** `setuptools` (через `pyproject.toml`).

## 2. Команды верификации (Как проверять свою работу)

Прежде чем делать коммит и создавать Pull Request, **обязательно** выполни следующие проверки.

```bash

source .venv/bin/activate
pip install -e ".[dev]"
```

**Запуск тестов:**

В репозитории нет строгой конфигурации линтеров (таких как `flake8`, `black`, `mypy`), но соблюдение стандартных PEP 8 правил крайне желательно. При внесении изменений старайся соответствовать стилю окружающего кода.

## 3. Архитектурные особенности и правила кодинга

*   **Ограничение ответственности (No LLM/Chat):** Этот шлюз предоставляет *только сырые данные*. Никаких LLM-прослоек или вызовов эндпоинтов `/chat`. Это чистый прокси для семантического поиска.
*   **Двухуровневый поиск (Hybrid Search):** Архитектура использует гибридный поиск:
    1.  **Векторный слой (AnythingLLM):** Взаимодействует через REST API (`/api/v1/workspace/.../vector-search`).
    2.  **Лексический слой (FTS5):** Используется локальная SQLite база данных (`lexical.db` с FTS5/BM25) в режиме "только чтение" (`mode=ro`).
*   **Работа с API-ключами:**
    *   Ключи **никогда не должны быть захардкожены**.
    *   Система ожидает `ANYTHINGLLM_API_KEY`, `MG_API_KEY`, `MG_AUTH_TOKEN` из переменных окружения (в основном, из `.env` файла).
    *   Всегда используй модуль `config.py` для доступа к настройкам и ключам (`config.TOKEN_RAW`).
*   **Обработка ошибок (Degraded Mode):** Функция гибридного поиска должна устойчиво работать при сбоях одного из слоев (например, при тайм-ауте API). Используй флаг `degraded=True` в ответе, если часть данных получить не удалось, но не роняй весь процесс. Обрати внимание на `gateway_health()`.
*   **Логирование:** В проекте используется собственный логгер (`logger.py`). Используй `log = get_logger()` в файлах, избегай простого `print()`.

## 4. Советы для будущих ИИ-агентов

1.  **Исследуй перед изменениями:** Начни работу с изучения `ARCHITECTURE.md` и `README.md`. Они содержат важный контекст, который поможет избежать ошибок в бизнес-логике.
2.  **Не трогай зависимости без нужды:** В `pyproject.toml` и `requirements.txt` строго определены зависимости. Не добавляй новые библиотеки (особенно тяжеловесные фреймворки вроде `FastAPI` или `LangChain`), так как проект задуман как легковесный шлюз.
3.  **Используй `config.py` как источник истины:** Любые пути к файлам (`MG_OPS_DIR`, `MG_LEXICAL_DB`) или URL-адреса должны браться из `config.py`.
4.  **Проверяй тесты после каждого изменения:** Поскольку архитектура критична к производительности и корректности доступа (особенно при гибридном поиске), малейшее изменение в логике мерджа результатов должно быть покрыто тестом. Запускай `pytest tests/test_gateway.py`.
5.  **Внимание к асинхронности (ее отсутствию):** В текущей реализации (v0.2.0) запросы к API с использованием `requests` выполняются синхронно, а не через `aiohttp`. Не пытайся внедрить `async/await` без явного на то указания, так как это потребует переписывания всего слоя поиска.
